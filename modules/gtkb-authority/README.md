# gtkb-authority

gtkb-authority 0.1.0 is the PostgreSQL schema, transaction and ordinary domain core in the GT-KB module model. It consumes gtkb-protocol 0.1.0 through public imports. This source candidate is under independent review. It is not an accepted or released artifact, and integration with the other modules is still ahead.

There is no published package and no supported install. The source can be built with Python, hatchling 1.29.0 and `python -I -B -m build --no-isolation`. Requires-Python >=3.11 is metadata; actual runtime qualification must name the interpreter and operating system used. The first target is Windows CPython 3.14 with Psycopg 3.3.4, Pydantic 2.13.3, FastAPI 0.139.0, Uvicorn 0.46.0 and tomlkit 0.13.3.

The public constructors are `PostgresSettings`, `AuthorityOperation`, `PostgresKernel`, `AuthorityService` and `create_authority_app`. Construction performs no database initialization or native activation. Supply an explicit absolute project root, an operation provider and a protected parameters provider. `PostgresSettings.service` is an opaque binding label. The parameters provider receives and checks that label against the selected protected binding. gtkb-authority never forwards a libpq service/profile name or loads private environment files.

The first transport accepts one explicit IPv4 loopback target with SCRAM password authentication. Required provider keys are host, hostaddr, port, dbname, user, password and sslmode. Both addresses are 127.0.0.1. Passwords stay in server memory and the protected provider channel. Verified TLS additionally requires explicit protected certificate and CRL paths; no weaker fallback follows an unsupported transport. Do not put credentials in HTTP, source, command arguments or logs.

An `AuthorityOperation` supplies the consumed catalog identity and digest, SQL lock and statement settings, connection polling, repository probe bound, page size, original deadline and checkpoint, and explicit disabled semantics. There are no live control defaults in these constructors. Use `gtkb_authority.controls` for the existing selected-root catalog parser, resolver, preview, digest-CAS setter, readback and compensation interfaces. Each outer operation captures one parameter and policy snapshot. Nested operations retain it; the next operation reads the provider again. An explicit isolated fixture artifact may supply test values without becoming a production authority.

`kernel.initialize()` initializes an admitted empty PostgreSQL target and validates the packaged schema and catalog metadata. `kernel.upgrade_schema(expected_schema_sha256=...)` applies only its exact supported predecessor transition. `kernel.status()` reports the actual selected database schema. Existing import/export methods are explicit migration tooling. Ordinary domain reads and writes never fall back to SQLite or cached data.

`AuthorityService` provides ordinary specification, test, project, membership, dependency, work-item, terminology, harness and planning operations. Mutations validate current version, classification and relationships and commit current/history changes in the same transaction. Public HTTP lists require an explicit limit; internal continuation uses the captured page size. Successful and refused responses use gtkb-protocol's canonical JSON codec. The client receives domain operations and public errors, never raw SQL or connection parameters.

`create_authority_app(service, project_root=...)` returns the ASGI application for an operator-owned Uvicorn listener. The operator owns its actual endpoint, listener, original process/task and streams. Absent native and context capabilities return a typed canonical 503 at their declared routes. An explicitly supplied native router mounts its own accepted routes and returns its real lifespan owner. Missing historical commit validation refuses before the protected transition. This version does not manufacture sessions, native roles, execution, context or finalization evidence.

The service owns its injected kernel's admission lifetime. Both expose `lifecycle_state()` with real state, active operation count and unresolved connection count. `close()` stops new work, preserves admitted original work and refuses an unresolved ending. After real settlement, explicit close completes and is idempotent. Closing and closed operations refuse before provider or database IO. There is no force-clear API. ASGI shutdown closes the actual supplied native lifespan and the owned service; the operator must still retain the original HTTP and PostgreSQL endings.

The loopback connector owns the returned `PGconn` directly through polling and setup. It discharges an original only after that same wrapper's `finish()` returns normally and its status is BAD. An inactive explicit `close()` makes one normal ending attempt per retained original. Unresolved originals and their failures stay owned; completed connection history is not accumulated in memory. A successful commit followed by an unproved connection ending reports `transaction_outcome=committed` and requires current/history readback before a retry. The exact Psycopg 3.3.4 `Connection(pgconn, row_factory=...)` constructor remains a source-backed compatibility boundary that needs review if the driver changes.

With a finite original deadline, internal domain statements refresh their PostgreSQL lock and statement settings against its remaining whole milliseconds. A sub-millisecond remainder refuses instead of disabling the server timeout. Checkpoints run between driver calls. These server limits and checkpoints do not guarantee interruption of blocked network I/O, driver transaction controls or a cancellation callback that changes during a statement.

Connection polling observes exceptional socket readiness as well as read/write readiness, including Windows refused-connect signaling. The internal guarded cursor exposes only execute, fetchone, fetchall and rowcount; it does not forward additional query methods around the guard. Normal finish return and the same wrapper's BAD status are the declared local ending receipt. BAD after finish is a driver wrapper consequence, not independent proof that a socket, server backend or remote work ended. A failed COMMIT acknowledgment remains an uncertain operation requiring current/history readback before any retry; this candidate does not yet provide a distinct structured unknown-commit outcome.
